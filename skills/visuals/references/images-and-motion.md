# Images, interaction and motion

Choose tools from the requested result, not a blanket code-only policy. Generated raster art,
SVG, existing animation libraries, engine tools and supplied assets are all options when
available and appropriate. Preserve editability and record relevant sources/usage rights.

Use images for appearance or analogy; keep exact technical labels and connections separately
editable. State where a metaphor stops. For games, concept art is intended direction and a
playable engine capture is observed behaviour; a camera pan on a still is not character animation.

Use interaction when a reader needs to vary a parameter, step an interleaving, inspect a state
or compare outcomes. Start with a small standalone HTML/SVG artifact. Do not create a full app
for a single demonstration. Reuse [Forge's existing motion examples](../../ui-design/examples/spatial-review/motion/README.md)
only when they reduce work; their optional backends are not prerequisites.

Animation should show a change that is hard to explain statically. Drive geometry, labels and
captions from the same model/time. Provide pause/replay/step controls as appropriate, keyboard
access and a meaningful reduced-motion/static view. Keep simulated inputs visibly distinguished
from measured traces. Inspect beginning, transitions, ending and loop reset.

For a requested video, establish length/aspect, source material, audience and audio/caption
needs. Start with a short representative segment; check it before rendering the full piece.
Use the existing [film example](../../ui-design/examples/spatial-review/motion-films.md) only if
its dependencies are already available or installation is authorized. Inspect the final encoded
file for decoding, clipping, readable captions, timing and audio when present. Avoid flashing
and report the limits of any automated checks. Do not claim export/playback from a source preview.

No automatic video generation for ordinary plans, and no imported character/3D/media framework
until an actual task requires it.
